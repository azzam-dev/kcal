## 1. المنتج في سطر واحد

تطبيق ويب عربي، جوال-أولاً، لتتبع السعرات والعناصر الغذائية الكبرى:
يُدخل المستخدم معلوماته مرة واحدة، فيحصل على هدف يومي محسوب، ثم يسجّل طعامه
بأقل عدد ممكن من الضغطات ويرى ما تبقّى له اليوم.

**المبدأ الحاكم لكل قرار:** أقل احتكاك ممكن. أي خاصية تزيد التعقيد بلا قيمة واضحة لا تُنفَّذ.

## 3. المعمارية

**مونوليث معياري مقسَّم حسب الميزة.** لا microservices ولا Clean Architecture كاملة:
تطبيق بمستخدم واحد يقرأ ويكتب بياناته الخاصة فقط، لا مكوّن يحتاج توسعاً مستقلاً،
ولا فريق منفصل يملك خدمة.

**المقايضة:** لو ظهرت معالجة ثقيلة لاحقاً (تحليل صور طعام مثلاً) فستحتاج نقلها إلى عامل
مستقل — وهو سهل لأن حدود الوحدات صريحة أصلاً.

### الطبقات

| الطبقة | المسار | القاعدة |
|---|---|---|
| الدومين | `src/features/*/domain` | تايبسكربت نقي: **لا React، لا Supabase، لا `fetch`**. هنا وحده تُختبر بالوحدة |
| الوصول للبيانات | `src/server/*` | استعلامات Supabase وحدها. لا معادلات، لا قواعد عمل |
| العرض | `src/app`, `src/components` | **لا يحوي أي معادلة تغذية إطلاقاً** |
| التفويض | Postgres RLS | لا في كود التطبيق. أي فحص في الكود حزام إضافي لا الحزام الوحيد |

**القاعدة الوحيدة التي لا تُكسر:** لا معادلة تغذية واحدة خارج `features/nutrition/domain`.
هذا ما يجعل تغيير معادلة BMR لاحقاً تعديل ملف واحد باختباراته، لا بحثاً في الشاشات.

### مسار البيانات في تسجيل وجبة

```
الشاشة → server action → تحقق Zod → دالة دومين نقية تحسب قيم الكمية
       → طبقة الوصول تكتب الصف → RLS تتحقق من الملكية في القاعدة
       → revalidatePath تحدّث الداشبورد
```

التجميع (المستهلك / المتبقي) يُحسب في الخادم باستعلام واحد،
لا بجلب كل السجلات وجمعها في المتصفح.

## 4. محرك الحساب

```
المدخلات ← BMR ← TDEE ← تعديل الهدف + حدود الأمان ← السعرات المستهدفة ← محرك الـmacros
```

### المعادلات

**BMR — Mifflin-St Jeor:**

| | |
|---|---|
| ذكر | `BMR = 10·kg + 6.25·cm − 5·age + 5` |
| أنثى | `BMR = 10·kg + 6.25·cm − 5·age − 161` |

**TDEE = BMR × معامل النشاط:**

| المستوى | المعامل |
|---|---|
| خامل | 1.20 |
| نشاط خفيف (1–3 أيام) | 1.375 |
| متوسط (3–5 أيام) | 1.55 |
| نشط جداً (6–7 أيام) | 1.725 |
| نشط للغاية | 1.90 |

**تعديل الهدف:**

| الهدف | التعديل |
|---|---|
| خسارة دهون | `TDEE × 0.80` |
| محافظة | `TDEE × 1.00` |
| زيادة | `TDEE × 1.12` |
| مخصص | `± (معدل kg/أسبوع × 7700 ÷ 7)` |

### حدود الأمان — مفروضة وقابلة للإعداد

- العجز لا يتجاوز **25%** من TDEE، والفائض لا يتجاوز **20%**.
- أرضية مطلقة: **1500 سعرة للذكر، 1200 للأنثى**.
- ~~ولا تنزل النتيجة تحت الـBMR أبداً~~ — **نُقض في 2026-09-06 قبل التنفيذ.** القاعدة
  كانت ستُفعَّل لكل مستخدم خامل يريد خسارة الدهون (1.20 × 0.80 = 0.96·BMR) وتعرض عليه
  تنبيه سلامة مقابل تغيير ٤٪. حدّ العجز ٢٥٪ يحصر أسوأ حالة عند 0.90·BMR.
  التفصيل في [DECISIONS.md](./DECISIONS.md).
- عند انتهاك أي حد: النتيجة **تُثبَّت عند الحد ويُعاد سبب واضح يُعرض للمستخدم** — لا تصحيح صامت.
- وزن مستهدف يعطي `BMI < 18.5` يُقبل مع تحذير صريح، ولا يُستخدم لتوليد عجز أشد.
- حد أدنى للعمر: **16 سنة**.
- مدخلات خارج المدى تُرفض في Zod **وفي `CHECK` في القاعدة** معاً.

### الـMacros — محرك منفصل خلف `MacroStrategy`

1. **البروتين أولاً:** 2.0 g/kg عند خسارة الدهون · 1.6 عند المحافظة · 1.8 عند الزيادة.
   **الوزن المرجعي = `min(الوزن الحالي، وزن BMI 25)`.**
2. **الدهون ثانياً:** 25% من السعرات ÷ 9، بأرضية 0.6 g/kg (ضرورية هرمونياً).
3. **الكربوهيدرات = الباقي** ÷ 4. لو خرج سالباً، يُخفَّض البروتين والدهون تناسبياً
   حتى الأرضيات ثم يُعاد سبب واضح.

إضافة كيتو أو نسب مخصصة لاحقاً = صنف جديد ينفّذ الواجهة، لا تعديل في المحرك.

## 5. نموذج البيانات

عشرة كيانات. كلها عليها RLS مربوطة بـ`auth.uid()`، وكلها لها ملف migration في الريبو.

| الجدول | الأعمدة الجوهرية | ملاحظات وفهارس |
|---|---|---|
| `profiles` | `id` (FK auth.users) · `display_name` · `gender` · `birth_year` · `height_cm` · `activity_level` · `training_days` · `goal` · `target_weight_kg` · `timezone` · `locale` | **سنة الميلاد لا العمر.** `training_days` للاقتراح لا للحساب |
| `nutrition_targets` | `user_id` · `effective_from` (date) · `bmr` · `tdee` · `calorie_target` · `protein_g` · `carb_g` · `fat_g` · `source` · `inputs` (jsonb) | **جدول إلحاقي، لا يُحدَّث أبداً.** `UNIQUE(user_id, effective_from)` |
| `foods` | `id` · `source` (seed\|user\|external) · `owner_user_id` · `name_ar` · `name_en` · `brand` · `barcode` · **لكل 100g:** `calories, protein, carbs, fat, fiber` · `search_doc` | فهرس GIN على `search_doc`. RLS: بذرة يقرأها الجميع، وأطعمة المستخدم لصاحبها فقط |
| `food_servings` | `food_id` · `label_ar` · `grams` · `is_default` | «حبة موز متوسطة = 118g» — هذا ما يجعل الإدخال سريعاً |
| `food_log_entries` | `user_id` · `log_date` · `meal_type` · `food_id` (nullable) · `quantity_grams` · **لقطة:** `name, calories, protein, carbs, fat` · `logged_at` | القلب. `INDEX(user_id, log_date)` |
| `saved_meals` | `user_id` · `name` | — |
| `saved_meal_items` | `saved_meal_id` · `food_id` · `quantity_grams` · `position` | مرجعي لا لقطة — الوجبة المحفوظة قالب حيّ يُعدَّل |
| `favorite_foods` | `PK(user_id, food_id)` | — |
| `weight_entries` | `user_id` · `recorded_on` (date) · `weight_kg` · `note` | `UNIQUE(user_id, recorded_on)` — الإعادة تُحدِّث لا تُكرِّر |
| الأطعمة الأخيرة | — | **لا جدول لها.** تُشتق باستعلام على السجل |

### قيود السلامة في القاعدة نفسها

`CHECK` على: الوزن 20–400كجم · الطول 90–250سم · الكمية `> 0` و`<= 5000g` ·
كل قيمة غذائية `>= 0` · السعرات `<= 900` لكل 100g (حد فيزيائي: الدهن النقي 900).

التحقق في Zod وحده لا يكفي — الكتابة قد تأتي من مسار آخر يوماً ما.

### حذف الحساب

`ON DELETE CASCADE` على كل جدول. حذف الحساب يحذف كل الصفوف فعلياً — لا «تعطيل» صامت.

## 6. طبقة الطعام والبحث

### التجريد

واجهة `FoodProvider` بثلاث دوال: `search(query)` · `getById(id)` · `getByBarcode(code)`.
في الـMVP تنفيذ واحد (`LocalFoodProvider` على جدول `foods`)؛ تنفيذات Open Food Facts أو
Nutritionix تُضاف لاحقاً خلف نفس الواجهة مع دمج النتائج.
**هذا ما يجعل قرار مصدر البيانات قابلاً للتراجع.**

### البحث العربي — تفصيل غير بديهي، ويجب أن يكون في أول migration للجدول

Postgres لا يملك قاموس بحث نصي للعربية. الحل: `pg_trgm` مع دالة تطبيع `IMMUTABLE`
تُستخدم **داخل الفهرس نفسه**:

- توحيد الألف: **أ إ آ ← ا**
- توحيد التاء المربوطة: **ة ← ه** · والألف المقصورة: **ى ← ي**
- حذف التشكيل والتطويل

بدون هذا، من يكتب «دجاج» لا يجد «دَجاج»، ومن يكتب «طماطة» لا يجد «طماطه».
هذه ليست تحسيناً لاحقاً — هي الفرق بين بحث يعمل وبحث لا يعمل.

### الترتيب

تطابق بادئة أولاً، ثم تشابه trigram، مع **رفع أطعمة المستخدم ومفضلته وأخيراته إلى أعلى
النتائج** — لأن هذا بالضبط ما يحقق «كلما تكرر الطعام صار تسجيله أسرع».

## 7. الـAPI

- **Route Handler واحد فقط:** `GET /api/foods/search?q=` — محمي بالجلسة، محدود المعدل،
  يعيد الحقول المعروضة فقط.
- **كل التعديلات server actions:** تسجيل/تعديل/حذف طعام · إضافة سريعة · وجبات محفوظة ·
  مفضلة · وزن · تحديث الملف والهدف · إنشاء طعام · حذف الحساب.
- **عقد الأخطاء:** `{ ok: true, data }` أو `{ ok: false, code, message }`.
  **لا يُعرض نص خطأ Postgres أو Supabase الخام للمستخدم أبداً.**
- **الداشبورد:** دالة Postgres واحدة تُعيد مجاميع اليوم + الهدف السارِي + الوجبات.

## 9. الواجهة والتجربة

### التنقّل — أربعة أقسام

**الرئيسية · الطعام · التقدّم · حسابي** (والأهداف داخل «حسابي»).

### الشاشات الأساسية

| الشاشة | الوظيفة الأولى | ملاحظة تصميم |
|---|---|---|
| الرئيسية | «كم تبقّى لي اليوم؟» | رقم السعرات المتبقية أكبر عنصر في التطبيق كله. حلقات الـmacros تحته، ثم الوجبات الأربع |
| بحث الطعام | الوصول للصنف بأقل ضغطات | **يفتح على الأخيرة والمفضلة قبل الكتابة**، لا على حقل فارغ. هذا يحوّل أغلب التسجيلات إلى ضغطتين |
| تفاصيل الصنف | ضبط الكمية | القيم تتحدث فورياً مع الكمية. أزرار حصص جاهزة (حبة / كوب / 100g) قبل الإدخال الرقمي |
| التقدّم | اتجاه الوزن | خط الوزن + **متوسط متحرك 7 أيام** — الوزن اليومي يتذبذب بالماء ويُقلق المستخدم بلا سبب |
| الأهداف | تعديل وإعادة حساب | يعرض «هذا التعديل يسري من اليوم» صراحةً، ويؤكد أن الأيام السابقة لن تتغير |

### قرارات مبنية على «أقل احتكاك»

- **الحذف بـtoast للتراجع، لا بحوار تأكيد.**
- **الإدخال في ورقة سفلية (bottom sheet)** لا صفحة كاملة — يبقي سياق اليوم مرئياً خلفه.
- **لوحة مفاتيح رقمية** على كل حقل كمية أو وزن (`inputMode="decimal"`)، والفاصلة العشرية العربية مقبولة.
- **تحديث متفائل** على إضافة الطعام، مع تراجع واضح عند الفشل.
- **حالات صريحة لكل شاشة:** فارغة · تحميل (هيكل عظمي لا دوّار) · خطأ بزر إعادة محاولة · نجاح.

### الهوية البصرية

داكن أولاً عبر توكنز CSS · خط عربي واضح بأرقام جدولية (`tabular-nums`) لأن التطبيق كله
أرقام متراصّة · مساحات على مقياس 4px · ثلاثة ألوان دلالية للـmacros فقط، لا للزينة ·
حركة محدودة بانتقالات الأوراق وتحديث الأرقام.

## 10. الأمان

| الخطر | الإجراء |
|---|---|
| وصول أفقي بين المستخدمين (IDOR) | RLS على كل جدول: `user_id = auth.uid()`. **مُختبَر آلياً بحسابَين حقيقيَّين** |
| SQL Injection | استعلامات مُعامَلة عبر supabase-js. أي دالة SQL مخصصة تأخذ معاملات لا سلاسل مركّبة |
| XSS | React يهرّب افتراضياً؛ ممنوع `dangerouslySetInnerHTML`. أسماء الأطعمة نص عادي |
| CSRF | server actions تتحقق من الأصل؛ كوكيز `SameSite=Lax` + `HttpOnly` |
| تحقق المدخلات | Zod على حدود الخادم + `CHECK` في القاعدة. طبقتان لا طبقة |
| تسريب معلومات | لا رسالة خطأ خام. رمز الخطأ يُترجم لرسالة عامة، والأصل يُسجَّل في الخادم فقط |
| إساءة استخدام البحث | حد معدل على `/api/foods/search` — نقطة النهاية الوحيدة القابلة للاستنزاف |
| الأسرار | `.env.local` خارج git، `.env.example` داخله. **مفتاح `service_role` لا يظهر في أي كود عميل** ولن نحتاجه في الـMVP |
| الخصوصية | لا نجمع ما لا نستخدمه. حذف الحساب يحذف كل الصفوف عبر `ON DELETE CASCADE` |
| التبعيات | عدد حزم صغير عمداً، مع `npm audit` في CI |

**المرحلة ١٠ مراجعة أمنية مستقلة** على كل بند أعلاه — لا فحص عابر في النهاية.

| تكامل | Vitest + Supabase | **اختبارات RLS بجلستَين حقيقيتَين:** مستخدم أ لا يقرأ ولا يعدّل ولا يحذف صف مستخدم ب في كل جدول · إعادة حساب الهدف لا تلمس الأيام السابقة · تعديل صنف طعام لا يغيّر سجلاً سابقاً |
| مكوّن | Testing Library | محرّر الكمية يعيد الحساب فورياً · نموذج الإضافة السريعة يرفض المدخلات غير الصالحة |
| طرف لطرف | Playwright | تسجيل ← onboarding ← هدف ← بحث ← تسجيل طعام ← الداشبورد يتحدث ← تسجيل وزن ← تعديل هدف · وتدفق الوجبة المحفوظة |

**قاعدة:** محرك الحساب **لا يُكتب قبل اختباراته**. هو منطق رقمي نقي بمدخلات ومخرجات معروفة —
أسهل شيء في المشروع للاختبار، وأخطر شيء لو أخطأ بصمت: مستخدم يتبع رقماً خاطئاً لأشهر ولا يلاحظ.

## 12. الأداء

- **الداشبورد باستعلام واحد** (دالة Postgres تُعيد المجاميع + الهدف + الوجبات)، لا أربعة.
- **لا N+1 في قائمة اليوم:** اللقطات المخزَّنة في صف التسجيل تعني أن عرض اليوم لا يحتاج
  ضمّ جدول الأطعمة إطلاقاً.
- **البحث:** فهرس GIN · حد 20 نتيجة · تأخير 150ms قبل الإرسال · إلغاء الطلب السابق.
- **مخطط الوزن:** SVG يدوي — يوفّر نحو 50KB مقابل مكتبة مخططات لخط واحد.
- **الفهارس:** `(user_id, log_date)` · `(user_id, recorded_on)` · GIN على البحث.
  لا فهارس تخمينية أخرى قبل قياس.
